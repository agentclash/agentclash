Fleet adds two optional control surfaces on top of orchestration: **budgets** (stop spending) and **scanners** (analyze finished transcripts).

## Budgets

Set a soft USD cap in the manifest:

```yaml
limits:
  budget_usd: 50
```

The expand API also returns a cost **estimate** from combination count and model hints so you can confirm before submit.

### Enforcement behavior

- The eval-set workflow checks remaining budget before launching pack sessions **and** before launching inner runs inside a multi-combination pack.
- When the budget is exhausted, further launches stop and the set settles with a budget-related failure/cancel path rather than silently overspending.
- Capacity waits (workspace run concurrency) use a long enough activity timeout to cover the internal poll window (on the order of minutes), so a brief full queue does not fail the set as a 5s activity timeout.

Exact settlement status strings are visible in `agentclash evalset status <id> --json`.

### Workspace emergency stop

A workspace admin can cancel every active eval set in a workspace:

```bash
agentclash workspace emergency-stop
```

The command asks for confirmation on a terminal. In a CI job, a script or any other non-interactive mode, it exits 64 with the error code `interactive_input_required` and cancels nothing. Pass `--yes` to cancel with no prompt:

```bash
agentclash workspace emergency-stop -w $WORKSPACE_ID --yes --json
```

The command cancels the eval sets and their runs only. Standalone runs and agent tryouts continue, so check them with `agentclash run list`. You cannot undo the cancellation.

The response includes how many sets were cancelled, their IDs and an audit event name (`workspace.emergency_stop`). The API form of the same call is:

```bash
curl -sS -X POST \
  -H "Authorization: Bearer $AGENTCLASH_TOKEN" \
  "$AGENTCLASH_API_URL/v1/workspaces/$WORKSPACE_ID/emergency-stop"
```

## Scanners

Scanners are post-hoc analyzers over completed case transcripts. They do not change scoring; they emit **findings** you can triage.

### Built-in catalog

Shipped under `runtime/scanners/catalog/`:

| Name | Intent |
|---|---|
| `reward-hacking` | Reward-seeking / metric gaming patterns |
| `tool-misuse` | Unsafe or policy-breaking tool use |
| `instruction-injection-compliance` | Prompt / instruction injection attempts |
| `sandbox-escape-attempt` | Escape or host breakout signals |

`instruction-injection-compliance` is an LLM judge: the worker sends each case transcript to its judge model. If the worker has no judge model, this scanner finds nothing. The other three scanners match patterns.

### Opt-in from the manifest

```yaml
scanners:
  - reward-hacking
  - tool-misuse
```

When present, a completed set can start a scan workflow for those scanners.

### Manual scan

Start a scan from the CLI:

```bash
# Run the scanners of the eval set manifest
agentclash evalset scan $EVAL_SET_ID

# Run two built-in scanners
agentclash evalset scan $EVAL_SET_ID --scanner reward-hacking --scanner sandbox-escape-attempt
```

- Without `--scanner`, the server runs the scanners of the manifest. If the manifest lists no scanner, the scan finds nothing.
- The CLI accepts only the names of the built-in catalog. An unknown name exits 64 and sends no request.
- The server starts the scan in the background and returns `202` at once.
- Only one scan of an eval set can run at a time. A second scan exits 1 with the error code `scan_already_running`. A set with manifest scanners starts its own scan when it completes, so a manual scan just after the completion can get this error.

List the findings, then change their triage status (`open`, `triaged` or `dismissed`):

```bash
agentclash evalset finding list $EVAL_SET_ID --severity high --status open
agentclash evalset finding update $FINDING_ID --status dismissed
```

- The list shows the newest findings first, 100 by default and 500 at most (`--limit`). If the count is equal to `--limit`, more findings can exist.
- The table leaves out the evidence text. Use `--json` to get the full findings, with the evidence.
- The CLI checks `--severity` (`low`, `medium`, `high`, `critical`) and `--status` before the request, because the server returns an empty list for an unknown value.

The API form of the same calls is:

```bash
curl -sS -X POST \
  -H "Authorization: Bearer $AGENTCLASH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"scanners":["reward-hacking","sandbox-escape-attempt"]}' \
  "$AGENTCLASH_API_URL/v1/eval-sets/$EVAL_SET_ID/scan"

curl -sS -H "Authorization: Bearer $AGENTCLASH_TOKEN" \
  "$AGENTCLASH_API_URL/v1/eval-sets/$EVAL_SET_ID/findings?severity=high&status=open&limit=100"

curl -sS -X PATCH \
  -H "Authorization: Bearer $AGENTCLASH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"status":"dismissed"}' \
  "$AGENTCLASH_API_URL/v1/scan-findings/$FINDING_ID"
```

Rescans that find nothing clear prior findings for that target/scanner/version so stale hits do not linger. A rescan that finds the same hit again keeps the triage status of the finding.
